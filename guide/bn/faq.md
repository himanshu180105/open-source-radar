# নতুনদের জন্য সচরাচর জিজ্ঞাসা (FAQ)

প্রথম pull request-এর আগে ও পরে মানুষ সবচেয়ে বেশি যে প্রশ্নগুলো করেন, তার সংক্ষিপ্ত উত্তর। প্রতিটি উত্তরে পূর্ণ বিবরণ সহ সংশ্লিষ্ট অধ্যায়ের লিংক দেওয়া আছে।

## শুরু করার আগে

### কোনো issue-এ কাজ শুরু করার আগে কি অনুমতি নিতে হবে?

প্রজেক্টভেদে আলাদা হয়। `CONTRIBUTING.md` দেখুন: কিছু প্রজেক্টে আগে মন্তব্য করতে বলা হয়, কিছু প্রজেক্টে `/claim` বা `/assign` command দিয়ে issue নিজের নামে নেওয়া যায়, আবার কিছু প্রজেক্টে সরাসরি PR খুলতে বলা হয়। গাইডে কিছু না থাকলে এবং issue-টি ছোট হলে সরাসরি pull request খোলা সাধারণত ঠিক আছে। বড় কিছুর ক্ষেত্রে আগে মন্তব্য করুন, যাতে কেউ সময় নষ্ট না করেন। দেখুন [অধ্যায় ৭](07-communication.md#একটি-issue-নিজের-নামে-নেওয়া)।

### সবার মতো না হয়ে আলাদাভাবে কীভাবে issue claim করবেন?

শুধু \"আমি কি এটিতে কাজ করতে পারি?\" বলবেন না। দুই-তিন বাক্যে বলুন আপনি কী খুঁজে পেয়েছেন এবং কী পরিবর্তন করতে চান। এতে maintainer হ্যাঁ বলতে পারবেন, অথবা code লেখার আগেই আরও ভালো পদ্ধতি জানাতে পারবেন। [অধ্যায় ৭](07-communication.md#একটি-issue-নিজের-নামে-নেওয়া)-এ একটি উদাহরণ আছে।

### কেউ সপ্তাহ আগে \"আমি নেব\" বলে মন্তব্য করে PR খোলেনি। আমি কি নিতে পারি?

আগে issue-তে জিজ্ঞেস করুন: \"আপনি কি এখনো এটিতে কাজ করছেন? না করলে আমি করতে চাই।\" কয়েক দিন উত্তর না পেলে maintainer-কে reassign করতে বলুন। না জিজ্ঞেস করে প্রতিযোগিতামূলক pull request খুলবেন না। দেখুন [অধ্যায় ৪](04-find-an-issue.md#কেউ-কি-ইতিমধ্যে-এটিতে-কাজ-করছেন)।

### একসঙ্গে কতগুলো issue claim করা উচিত?

একটি। প্রথম pull request খোলার পরে পরবর্তীটি claim করুন।

### আমি নিশ্চিত না যে শেষ করতে পারব। তবুও কি চেষ্টা করব?

হ্যাঁ, তবে এমন কিছু বেছে নিন যার পরিধি আপনি অনুমান করতে পারেন। এক ঘণ্টার মধ্যে সমস্যাটি reproduce করতে এবং সংশ্লিষ্ট code খুঁজে পেতে পারলে সেটি সম্ভবত উপযুক্ত। আটকে গেলে issue-তে বলুন এবং নিজের নাম সরিয়ে নিন। দেখুন [অধ্যায় ৪](04-find-an-issue.md#আপনি-কি-এটি-শেষ-করতে-পারবেন)।

## নিয়ম ও আনুষ্ঠানিকতা

### একটি bot আমাকে CLA সই করতে বলেছে। এটি কি স্বাভাবিক?

হ্যাঁ। Contributor License Agreement প্রজেক্টকে আপনার পরিবর্তন ব্যবহারের অধিকার দেয়। একবার অনলাইনে সই করলে পরবর্তী contribution-এও প্রযোজ্য হয়। ভালোভাবে পড়ুন এবং employer-এর হয়ে contribution করলে তাদেরও সই করতে হবে কি না দেখুন। দেখুন [অধ্যায় ৬](06-rules-before-you-start.md#contributor-license-agreement-cla)।

### DCO check ব্যর্থ হয়েছে। কীভাবে ঠিক করব?

প্রতিটি commit-এ একটি `Signed-off-by:` line থাকতে হবে, যা commit author-এর তথ্যের সঙ্গে মিলবে। আপনার branch-এর সব commit-এ যোগ করে আবার push করুন:

```bash
git rebase --signoff upstream/main
git push --force-with-lease
```

এরপর থেকে `git commit -s` ব্যবহার করুন। দেখুন [অধ্যায় ৬](06-rules-before-you-start.md#developer-certificate-of-origin-dco)।

### AI টুল ব্যবহার করা যাবে?

শুরু করার আগে প্রজেক্টের নীতি যাচাই করুন। কিছু প্রজেক্ট AI-তৈরি contribution নিষিদ্ধ করেছে, কিছু জানাতে বলেছে, আবার অনেক প্রজেক্ট কিছু বলেনি। নিয়ম যাই হোক, প্রতিটি লাইনের দায়িত্ব আপনার: বুঝুন, পরীক্ষা করুন এবং review-এ ব্যাখ্যা করতে প্রস্তুত থাকুন। দেখুন [অধ্যায় ৬](06-rules-before-you-start.md#ai-এর-সাহায্যে-তৈরি-contribution)।

### একটি bot আমার PR বন্ধ করে দিয়েছে বা spam চিহ্নিত করেছে। এখন কী করব?

bot-এর বার্তাটি পড়ুন। অনেক প্রজেক্ট প্রথমবারের contributor-দের PR বন্ধ করে দেয় যদি সেটি কোনো issue-এর সঙ্গে যুক্ত না থাকে অথবা template অনুসরণ না করে। যা বলা হয়েছে তা ঠিক করুন, অথবা ভদ্রভাবে উত্তর দিয়ে maintainer-কে দেখতে অনুরোধ করুন। দেখুন [অধ্যায় ৬](06-rules-before-you-start.md#anti-spam-এবং-প্রথমবারের-contributor-দের-জন্য-automation)।

## Pull request খোলার পরে

### কেউ উত্তর দেয়নি। কতক্ষণ অপেক্ষা করব?

এক-দুই সপ্তাহ স্বাভাবিক। এরপর একটি সংক্ষিপ্ত, ভদ্র মন্তব্য করুন যে আপনার কাছ থেকে কিছু দরকার কি না। অপেক্ষার সময় branch-টিকে conflict-মুক্ত রাখুন। এক মাস পরে জিজ্ঞেস করুন পরিবর্তনটি এখনো দরকার কি না। দেখুন [অধ্যায় ৮](../08-reviews.md#when-nothing-happens)।

### CI red হয়ে আছে এবং কারণ বুঝছি না।

ব্যর্থ job-টি খুলুন এবং শেষ error নয়, প্রথম error-এ যান। একই command স্থানীয়ভাবে চালান। আপনি যে code স্পর্শ করেননি সেখানে failure হলে pull request-এ বলুন; এটি একটি flaky test বা main branch-এর সমস্যা হতে পারে। দেখুন [অধ্যায় ৮](../08-reviews.md#when-ci-fails)।

### Maintainer পরিবর্তন চেয়েছেন। নতুন PR খুলব?

না। একই branch-এ আরও commit push করুন, pull request স্বয়ংক্রিয়ভাবে আপডেট হবে। প্রতিটি মন্তব্যের উত্তর দিন যাতে reviewer জানতে পারেন কাজটি হয়ে গেছে। দেখুন [অধ্যায় ৮](../08-reviews.md#when-you-get-change-requests)।

### আমার PR-এ merge conflict আছে।

প্রজেক্টের main branch থেকে আপনার branch আপডেট করুন, conflicting লাইনগুলো ঠিক করুন এবং push করুন:

```bash
git fetch upstream
git rebase upstream/main
# fix the files, then: git add <file> && git rebase --continue
git push --force-with-lease
```

দেখুন [অধ্যায় ৫](../05-first-pull-request.md)।

### আমার PR merge না হয়েই বন্ধ করা হয়েছে। আমি কি ভুল করেছি?

সবসময় না। হয়তো অন্য কেউ আগেই সমস্যাটি সমাধান করেছেন, অথবা প্রজেক্ট ভিন্ন পদ্ধতি চায়। কারণটি পড়ুন, ধন্যবাদ জানান এবং সংশোধিত সংস্করণ কাজে লাগবে কি না জিজ্ঞেস করুন। দেখুন [অধ্যায় ৮](../08-reviews.md#when-your-pull-request-is-closed)।

## Merge-এর পরে

### ছোট প্রজেক্টে merge হওয়া PR কি গণনায় আসে?

হ্যাঁ। merge হওয়া pull request প্রকাশ্যে করা আসল কাজ, প্রজেক্টের আকার যাই হোক। আপনি যে প্রজেক্ট পছন্দ করেন সেখানে কয়েকটি merge হওয়া পরিবর্তন অনেক repository জুড়ে ছড়িয়ে দেওয়া একলাইনের অনেক fix-এর চেয়ে মূল্যবান। দেখুন [অধ্যায় ৯](../09-keep-going.md)।

### পরবর্তী কী করব?

একই প্রজেক্টে থাকুন। আপনি ইতিমধ্যে জানেন কীভাবে এটি build করতে হয় এবং maintainer-রা কীভাবে review করেন। একটু বড় issue বেছে নিন, নতুন issue-এর triage-এ সাহায্য করুন অথবা অন্য কারো pull request review করুন। দেখুন [অধ্যায় ৯](../09-keep-going.md)।
